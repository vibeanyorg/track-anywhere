# Track Anywhere Everyday Entry Gateway 完整设计

**副标题：** 面向自然语言的人类接口，面向 Agent 的精确记账协议  
**代码快照：** `track-anywhere-20260724-143206.zip`  
**日期：** 2026-07-24  
**状态：** Proposed Design / Code Review

> 核心命题：人类只需说清楚“发生了什么”；Agent 只提交业务事实；服务端独占会计决策，并原子生成可审计的复式账。

## 0. 结论先行

当前 Track Anywhere 的账本内核并不差。事件溯源、精确整数金额、复式平衡、幂等、并发、同步投影、隐私 sidecar、信用卡关系等基础设施都较扎实。真正缺失的是位于自然语言入口与复式账本之间的 **Everyday Entry Gateway（语义记账网关）**。

当前 MCP/CLI/REST 将不同抽象层混在一起：普通支出工具隐藏了借贷方向，却要求 Agent 选择 `expense_account_id`；分类又只能通过低层 reporting line 单独写入；全局工具说明同时谈读侧整数 `units` 与写侧十进制 `amount`。这导致“外卖分类被建成支出账户”“660 元被解释为 6.60 元”“一次使用暴露一个新 bug”。

推荐保持“复式账本内核 + 独立业务分类”的方向，并新增统一语义层：

1. 人类接口保持自然语言或友好 CLI。
2. Agent 使用场景化、结构化的 prepare 工具，不接触借贷、posting、system account、category version、canonical units。
3. 服务端解析账户和分类，决定会计分录，并将 journal/card event、reporting line 和加密 narrative 原子提交。
4. 旧 raw REST/CLI 保留给迁移、调试和高级会计；旧 MCP 写工具退出普通 Agent surface。

## 1. 本轮 Review 的修正意见

此前为了先写入“买水 660 元”，创建了 `临时支出-待分类（饮料）` 账户。这在操作上完成了写入，但在产品和数据模型上并不是正确修复：它继续扩大了“业务分类 = 支出账户”的目录债务。该记录应视为待迁移数据，待新语义入口上线后通过冲销和重记修复，并关闭临时账户。

更完整的 Review 得出以下修正：

- 不应继续给旧工具补分类名、金额说明等局部补丁；需要统一语义入口。
- 不应把 Category 合并回 Expense Account；现有独立分类和 reporting line 方向是合理资产。
- 不应给 Agent 暴露一个包含大量可选字段的巨大工具；MCP 应按高频场景拆成简单 prepare 工具，共享同一个服务端编译器。
- 金额精确性不能只依赖 prompt。外部金额协议必须显式区分资产主单位与次单位，裸数字永远默认主单位。
- “准备/确认”是短生命周期的语义意图，不是恢复已删除的 V1 会计 Draft；不得进入不可变账本事件。
- 还需要语义读模型、重复检测、账户/分类解析、错误码和端到端 golden scenarios，不能只修写接口。

## 2. 代码审计发现

### 2.1 已有基础值得保留

- `accounts` 与 `categories/category_versions` 是独立模型；分类具有父子层级和不可变版本。
- `ReportingLinesAssigned` 已经把 category 作为独立 reporting dimension 绑定到交易，而不是作为 posting account。
- `LedgerWritePlan.events` 支持单次提交多个事件；`LedgerCommitter.append_and_project` 在一个事务中顺序 append + projection。
- 金额底层使用精确整数 units，写侧 `PlainDecimal` 转换职责在后端。
- 信用卡 charge/payment/refund/fee 有独立语义与关系投影。
- 事件 payload 禁止 merchant/memo 等敏感文本；protected content sidecar 提供加密存储。

### 2.2 根因一：MCP 是“半语义、半底层”

`ledger_record_expense` 需要 `source_account_id + expense_account_id`，但没有 `category_id`。`ledger_record_credit_card_charge` 同样要求 expense account。与此同时，`ledger_create_account` 允许普通 Agent 创建 `expense/income/equity/fund` 账户。Agent 收到“外卖”后，把它当成支出账户并不是偶然，而是工具契约在诱导该行为。

### 2.3 根因二：分类写入与账本写入分离

分类只能通过 `AssignReportingLinesCommand` 写入，并要求 line ID、line version ID、category version ID、canonical integer units 等低层字段。当前实现先查询已投影交易再校验，因此常规调用必须“先记账，再分类”。第二步失败会产生已入账但未分类的交易。

### 2.4 根因三：金额单位语义泄漏

MCP 全局说明强调 integer units，但没有清楚区分：读取响应中的 `units` 是底层整数；写工具的 `amount` 是人类主单位十进制。后端正确地把 `amount="660"` 转成 CNY `66000` units，但 Agent 可能在调用前自行除以 100。该错误可能造成 100 倍金额偏差。

### 2.5 根因四：CLI/REST/MCP 能力漂移

CLI 的 `ta tx record` 和 `ta tx classify` 是 raw ledger 操作；REST 同样以 postings/reporting lines 为中心；MCP 只覆盖四个半语义写场景。收入、退款、拆分、重复截图、自然语言账户解析等能力没有统一实现，各入口会逐步漂移。

### 2.6 根因五：测试验证了内核，没有验证用户任务

现有测试对权限、幂等、未知提交结果、系统账户隔离、事件与投影很扎实，但缺少“自然语言 -> Agent 调用 -> 最终分录 + 分类”的 golden scenarios。MCP evaluation 主要覆盖读取问题，因此接口契约可通过而真实体验持续出错。

## 3. 目标产品模型

### 3.1 四个清晰概念

1. **资金账户 Account**：现金、储蓄卡、电子钱包、信用卡等，负责余额和负债。
2. **内部会计账户 Internal Account**：expense clearing、income clearing、balance adjustment、FX 等，由服务端使用，不向普通用户或 Agent 暴露。
3. **业务分类 Category**：食品/外卖、交通/打车、软件订阅/AI 工具等，用于预算和分析，不是支付账户。
4. **交易叙述 Narrative**：商户、渠道、订单号、备注、原价、优惠、截图来源等，存储在加密 sidecar。

### 3.2 核心不变量

- 普通外部接口永远不能指定 debit/credit、posting ID 或内部 clearing account。
- 普通支出必须同时产生平衡分录和完整分类；默认不允许部分分类。
- Category ID 不能出现在 posting account 字段；Account ID 不能出现在 category 字段。
- 普通记账流程不自动创建账户或分类。
- 裸数字金额默认资产主单位；系统绝不因为“看起来不合理”而静默改金额。
- 信用卡还款属于资产负债转移，分类必须为空。
- 退款引用原交易并继承分类；复杂拆分退款必须澄清。
- 所有修正通过 reversal + replacement，历史事件不可直接更新。

## 4. 推荐架构

```text
人类自然语言 / 截图 / 友好 CLI
                 |
                 v
Agent Adapter：提取业务事实，不做会计决策
                 |
                 v
Everyday Entry Gateway
  - Amount normalizer
  - Account resolver
  - Category resolver
  - Duplicate detector
  - Policy / clarification engine
  - Entry compiler
                 |
                 v
LedgerWritePlan（一个 Book lock + 一个 DB transaction）
  1. JournalTransactionPosted 或 CreditCardTransactionRecorded
  2. ReportingLinesAssigned
  3. Protected Narrative Sidecar
                 |
                 v
Event Store + Synchronous Projections + Semantic Read Model
```

## 5. 统一领域契约

服务端内部使用 discriminated union：

- `ExpenseEntryInput`
- `IncomeEntryInput`
- `TransferEntryInput`
- `CreditCardPaymentEntryInput`
- `RefundEntryInput`
- `AdjustmentEntryInput`
- P1：`FxEntryInput`、`InvestmentEntryInput`

金额输入：

```json
{
  "value": "660",
  "denomination": "asset_unit",
  "asset_code": "CNY",
  "source_text": "660"
}
```

规则：

- `value=660, denomination=asset_unit` -> ¥660.00。
- `value=660, denomination=minor_unit` -> ¥6.60（仅适用于支持次单位的法币）。
- `source_text` 由自然语言/截图适配器提供，用于一致性审计和异常提示。
- Agent 永远不能提交 ledger units。

账户和分类引用支持稳定 ID 或查询：

```json
{"account_id": "..."}
```

或：

```json
{"query": "工商银行信用卡", "last4": "1242", "subtype": "credit_card"}
```

分类：

```json
{"path": ["食品", "外卖"]}
```

或：

```json
{"query": "外卖"}
```

## 6. Prepare / Commit 协议

`PreparedEntry` 是短生命周期、可过期的语义意图，不是会计事件。

### Prepare 返回状态

- `ready`
- `needs_clarification`
- `duplicate_suspected`
- `unsupported`

并返回：

- `intent_id`
- opaque `commit_token`
- `expires_at`
- 人类可读 preview
- resolved IDs（供 Agent 校验，不展示给普通用户）
- warnings 与结构化 clarification options

### Commit

只接受：

```json
{"intent_id": "...", "commit_token": "...", "request_id": "..."}
```

提交阶段不得重新传金额、账户、分类或时间，以避免 preview 与最终账务漂移。Commit 重新校验账户状态、分类版本、重复风险、Book write state 和 intent 是否过期。

建议将 prepared intents 存入短期数据库表，私密叙述加密；token 只保存随机引用和哈希，不包含商户/备注明文。

## 7. MCP 设计

面向 Agent 的工具应按场景拆分，避免一个巨大 oneOf schema：

- `ledger_prepare_expense`
- `ledger_prepare_income`
- `ledger_prepare_transfer`
- `ledger_prepare_credit_card_payment`
- `ledger_prepare_refund`
- `ledger_prepare_adjustment`
- `ledger_commit_entry`
- `ledger_cancel_entry`（可选）

所有 prepare 工具调用同一个 backend service/entry compiler；只是在 MCP 层提供更小、更明确的参数 schema。

普通 Agent surface 应隐藏/废弃：

- 旧 `ledger_record_expense`
- 旧 `ledger_record_credit_card_charge`
- 可创建 expense/income/equity/fund 的 `ledger_create_account`
- raw journal posting 工具

普通账户创建只允许 asset/liability；投资账户通过专用流程创建。高级会计工具放入显式 `raw/admin` surface，默认 Agent 不可见。

## 8. 友好 CLI 设计

```bash
ta expense 660 --from "微信零钱通" --category "食品/饮料" --at now
ta income 12000 --to "工商银行 6184" --category "工资/heyrevia"
ta transfer 1000 --from "中国银行 2950" --to "微信零钱通"
ta card-pay 2000 --from "工商银行 6184" --card "工商银行信用卡 1242"
ta refund 10 --original <transaction-id>
ta reconcile "微信零钱通" --actual 1250.60
```

公共选项：

- `--dry-run`：只 Prepare。
- `--yes`：在无 warning 且唯一解析时自动 Commit。
- `--json`：输出稳定机器协议。
- 默认 Book、时区和币种来自 profile/book settings。
- request ID、transaction ID、posting ID、stream version 全部自动处理。

现有低层命令保留并迁至 `ta raw ...`，用于迁移、调试和高级复式账。

## 9. 服务端编译规则

### 普通资产账户支出

```text
借：Internal Expense Clearing CNY
贷：微信零钱通 / 储蓄卡
分类：ReportingLineKind.EXPENSE + category version
```

### 信用卡消费

```text
借：Internal Expense Clearing CNY
贷：信用卡负债
关系：credit_card_charge
分类：expense category
```

### 收入

```text
借：收款资产账户
贷：Internal Income Clearing CNY
分类：income category
```

### 转账

```text
借：目标资产账户
贷：来源资产账户
分类：空
```

### 信用卡还款

```text
借：信用卡负债
贷：付款资产账户
分类：空
```

### 退款

- 信用卡退款：复用现有 typed relation，继承原 reporting lines，退款在月度汇总中符号为负。
- 非信用卡部分退款：新增明确的 refund transaction kind/event，方向为资产借、expense clearing 贷，reporting sign 为负。
- 原交易单分类：自动继承。
- 原交易多分类：全额退款复制原分配；部分退款默认要求用户指定分配，或采用明确的比例策略并展示预览。

### 优惠

复式账只记录实际支付 net amount。原价、优惠、红包等进入加密 narrative：

```json
{
  "gross_amount": "4.55",
  "discount_amount": "0.50",
  "net_amount": "4.05"
}
```

## 10. 内部账户角色

扩展 `AccountSystemRole`：

- `expense_clearing`
- `income_clearing`
- `balance_adjustment`
- `fx_trading`

内部 clearing 保持 `account_type=expense/income`，以保留总账 P&L 语义，但设置 system role 并从普通接口隐藏。服务端按 `(book_id, asset_code, system_role)` 唯一解析。

由于数据库已禁止修改 account type/system role 等会计身份，现有 `System expense CNY` 无法安全就地升级。推荐创建新的 canonical internal accounts，未来交易只使用新账户；旧账户作为 legacy 保留或关闭，不直接篡改历史。

## 11. 分类与解析策略

建议在 category version 中增加 `usage_kind=expense|income|both`，历史版本保持不变。解析顺序：

1. 精确 category ID。
2. 精确完整路径。
3. 用户保存的 alias。
4. 在当前 usage kind 内精确规范化名称。
5. 用户私有 merchant/category rule。
6. 语义候选。
7. 多候选或低置信度时返回澄清。

禁止在记账流程中自动创建 category。美团等平台不能硬编码为外卖，因为其可代表打车、酒店、团购等多种用途。

账户解析同理，并先按场景过滤类型。例如支出支付账户只允许 asset 或 credit-card liability；信用卡还款目标只允许 liability/credit_card。

## 12. 原子性

新的 compiler 直接从拟写入 postings 验证 reporting allocations，而不是先查询已投影交易。它生成同一个 `LedgerWritePlan`：

1. journal/card event；
2. reporting event；
3. 同事务内保存 protected narrative。

现有 `LedgerCommitter` 已能在一个 Book lock 和数据库事务内 append 多事件并顺序应用投影。需要抽离 `assign_reporting_lines` 的纯校验/事件构建逻辑，并新增原子性集成测试。

## 13. 隐私与语义读模型

保持不可变事件不含商户、备注、订单号和截图文本。不要直接扩展当前严格三字段 decoder；新增版本化的 `transaction_narrative_v2` protected content kind，并提供 v1/v2 upcaster。

新增 `EverydayEntryView`：

- transaction/entry ID
- kind
- 人类主单位金额与币种
- payment/source/target account display
- category path
- merchant/channel（授权后解密）
- occurred_at
- refund/reversal links
- raw journal reference

MCP 和友好 CLI 使用该 read model 返回回执；原始 journal 查询继续保留给审计。

## 14. 重复检测

request ID 只能防止同一请求重试，不能防止重复截图/重复导入。新增：

- provider/order external reference：强去重。
- source fingerprint：基于来源、订单号、金额、时间、账户等规范化字段；敏感字段使用 HMAC。
- 无明确外部 ID 时做软重复检测，返回 `duplicate_suspected`，不得静默跳过或重复写入。

## 15. 当前数据修复

已确认：

1. “外卖”同时存在 Category 和 `account_type=expense` 账户；¥53 交易直接借记了外卖账户。
2. 临时账户 `临时支出-待分类（饮料）` 被用于买水 ¥660 交易。
3. `通讯 / 手机话费` 等其他业务型 expense accounts 需要审计。

修复流程：

1. 禁止旧入口继续产生此类数据。
2. 创建 canonical internal clearing accounts。
3. dry run 扫描同名/近似 category-account、交易数、金额和时间范围。
4. 对每笔错误交易生成 reversal + replacement；replacement 使用 internal clearing 并原子附加 category。
5. 验证账户归零、月度分类汇总和余额一致。
6. 关闭误创建账户，保留历史审计。
7. migration 使用稳定 idempotency key，可安全重复执行。

## 18. 验收标准

- 人类只说自然语言或使用简单 CLI，不接触会计字段。
- Agent 不接触 debit/credit、posting、system account、category version、ledger units。
- 裸数字 660 永远是 660 主单位，除非明确标注次单位。
- 普通支出和分类要么一起成功，要么一起失败。
- 信用卡还款不计入支出。
- 退款关联原交易并正确冲减分类。
- 普通记账不会创建账户或分类。
- CLI、MCP、REST 使用同一 service 和 compiler。
- 任何错误数据都有可审计的 reversal/replacement 路径。
- golden scenarios 在 PostgreSQL、REST、MCP、CLI 四层全部通过。

## 21. 最终决策

推荐选择：**复式账本内核 + 独立分类 + Everyday Entry Gateway**。

不选择“分类就是 Expense Account”，因为它会把支付账户、会计账户和消费用途重新混在一个 catalog，给人类和 Agent 都造成歧义；也不选择“继续修旧 MCP”，因为旧接口的抽象边界本身错误。

正确的产品边界是：

> Agent 负责理解“发生了什么”，服务端负责决定“账该怎么做”。
